1. Overview ภาพรวม

STI KPI is a Tier 1, standalone intranet app at http://sti-apps:8080/kpi. It holds every KPI from company to team (2027) and person (2028) in the two layers of the STI KPI framework: Base KPIs for the running job and Goal KPIs cascaded from the goal and strategies S1–S4. All are tracked monthly and reviewed quarterly and at year end. It replaces scattered Excel files with one register, one scoring rule and one audit trail.

Why Tier 1. Two of the standard's four tests are true: more than one department depends on it (every division, the Council, the MD), and from 2028 it writes audited data (individual results are HR records and may feed pay).

Why a standalone app, not a Portal module. Each app has its own App Pool and JWT signing key, so a leak elsewhere cannot mint a token that reads 2028 individual results. The STI Portal links to /kpi; it does not host it.

In scope: KPI register, target approval, monthly actuals with RAG and evidence, scoring, quarterly and year-end reviews, dashboards, ERP feed for production KPIs (2027); individual KPIs, self and manager assessment, HR calibration, privacy controls (2028).

Out of scope: payroll and bonus calculation, a full HR system, replacing the ERP.

Supersedes the plan's technology section. The 27 Oct plan took its stack from the older IT roadmap (ASP.NET Core 8 MVC, jQuery, Windows Auth, EF Core). The August 2026 standard replaced that roadmap; this document follows the standard.

2. Architecture สถาปัตยกรรมระบบ

One ASP.NET Core API on IIS serves the React SPA from wwwroot, accepts sign-ins from STI Main, runs the background jobs and is the only writer to sti_kpi. It sits behind the STI YARP gateway on port 8080 and never talks to Active Directory itself.

Deployment

  • Ports 5230 (API) and 5330 (Vite dev), recorded in the port registry (Standard/docs/06-deploy.md).
  • Gateway routes kpi-bare (/kpi) and kpi-all (/kpi/{**catch-all}) to cluster kpi → http://localhost:5230/.
  • App:PathBase = /kpi; base: '/kpi/' in vite.config.ts; basename="/kpi" on the router.
  • Server folders D:\STI\apps\kpi\{releases, current, shared\{config, logs, data\uploads}}.
  • App Pool STI.Kpi: No Managed Code, AlwaysRunning, recycle 04:30 (after the DW ETL).
  • SSO registration in STI Main's sso-clients.json: clientId sti-kpi, a secret of at least 32 characters, redirectUris = the KPI callback URL exactly, signoutUrl = /kpi/api/auth/signed-out. STI Main is restarted to load it.
  • KPI config in shared\config\appsettings.Production.json: Auth:Mode = sso, Auth:Sso:Issuer (STI Main's SSO_ISSUER), Auth:Sso:BaseUrl, ClientId, ClientSecret, and KPI's own Auth:Jwt:Key. Never in the repository.
  • Network: the KPI server must reach STI Main over HTTPS (code exchange, JWKS) and STI Main must reach KPI's sign-out URL. Both hops cross hosts (STI Main runs on the Linux Docker host, KPI on IIS), so the firewall and certificate trust need checking.
  • Build: npm run build (tsc -b clean) → dotnet publish -c Release with 0 errors and 0 warnings. Never build on the server.

Base and Goal KPIs

The app follows the two-layer framework (STI_KPI_Framework_Summary_EN-TH.md): Base KPI + Goal KPI = Total KPI. Each KPI carries layer. Both layers share the same targets, monthly entry, scoring, reviews and audit; they differ only in the rules below, not in separate screens.

Parent linkNot required. An optional strategy_id marks it goal-linked: a goal that improves an existing KPI raises its target instead of creating a second KPIRequired: a strategy or a parent Goal KPI. Approval rejects an orphan

ShownRegister, entry grid and boards show a Base / Goal badge and filter (layer=). The KPI tree shows Goal KPIs under their strategy, and goal-linked Base KPIs with a link marker

Weight split: a soft warning, never a block. Every KPI set (a team's now, a person's from 2028) shows the share of weight on Base and on Goal KPIs. When the Base share is outside the range for that level, an amber notice appears on the draft and in the approval view, so the approver sees it before deciding. Submit and approve still work, and the reviewer can note why the set differs. Ranges live in scoring_rule.layer_split_json, editable per cycle in Admin. Starting values from the framework:

LevelBase KPI weightGoal KPI weight
Manager50–60%40–50%
Supervisor~70%~30%
Operator80–90%10–20%
Division / team set (2027)To agree with the strategy team in Phase 0 (open item); no warning until set

The same check gives a soft warning when a set holds more than 8 KPIs (the framework suggests about 5–8 per person). Scoring does not change: Σ(weight × score) ÷ Σ(weight) across both layers.

Scoring rules

The rules live in one C# class, Features/Scoring/ScoringService.cs. They are mirrored in src/features/scoring.ts only for instant feedback while typing; the server value is the one stored. Both are tested against the same table of cases.

DirectionAchievement
upactual ÷ target; if target = 0, any positive actual = cap
downtarget ÷ actual; if actual ≤ 0, cap
range1.0 inside [target_low, target_high]; outside, distance-based (rule still to agree with HR)
passpass = 1.0, fail = 0

Achievement is capped at 120% by default. The period value uses the KPI's aggregation: avg of months with data, or last for cumulative KPIs. Team score = Σ(weight × score) ÷ Σ(weight), over approved KPIs that have a result.

ERP and data-warehouse feed

Production KPIs (OEE, %NG, breakdown downtime, on-time delivery, first-lot pass) have source = erp and are never typed in.

  • Preferred source: the Resin data warehouse (MySQL 8, nightly ETL 02:30–04:00), read through a read-only account. It already cleans VARCHAR dates, Buddhist-era years and mixed collations.
  • Fallback until the DW is live: SELECT-only queries against pps2 through the read-only ERP connection, using ErpDate and exclusive upper bounds. No views or other objects are created in pps2.
  • ErpImportJob runs on the 1st working day at 08:00 for the month just closed, writes kpi_actual rows and logs an erp_import_run.
  • Each ERP KPI's query is named by kpi.source_ref and lives in code (ErpKpiQueries.cs), parameterised. No SQL is stored in the database.
  • An owner can comment on an ERP value but not overwrite it. A wrong value is fixed at the source and re-imported.
  • Known limit: hourly production and downtime data are complete only from Apr–May 2026, so earlier OEE baselines are not comparable.

Core flows

  1. Set targets (January). A team starts from its Base KPIs carried from last year (in 2027, seeded from the 2026 inventory) and adds the Goal KPIs cascaded to it, each linked to a parent KPI or a strategy, with baseline, target and weight. The draft shows the Base / Goal weight split, with an amber notice if it is outside the agreed range. Submit → approve or return with a comment. Route: team KPI → division head; division KPI → Council; strategy KPI → Executive.
  2. Track (monthly). The entry grid shows each KPI's target, last value and RAG. Actuals are due by the 5th working day; a comment is required for amber and red. ERP KPIs arrive by import and are read-only. Late entries trigger reminders and a "not updated" flag on the board.
  3. Quarterly review (Apr, Jul, Oct). The form is pre-filled with the quarter's actuals and scores. Owner self-assesses, reviewer assesses; highlights, issues, actions (owner, due date) and change requests are recorded, then signed. Open actions carry forward.
  4. Year-end review (January). Final actuals are locked; achievement and weighted score are computed; owner, reviewer and executive sign. Each KPI is kept, changed or retired for the next cycle; Base KPIs default to keep.

API contract

Everything follows Standard/docs/02-api-contract.md.

  • Envelope { success, message, data, pagination? }. message is shown to staff verbatim, in the user's language (Accept-Language: th|en).
  • Paths lower-kebab plural (/api/kpis, /api/review-actions); query and JSON camelCase.
  • Lists accept page, pageSize (cap 200), search, sort (whitelist per endpoint).
  • GET /api/health is anonymous and reports database, dw and sso (STI Main JWKS reachable) status.
  • Auth endpoints: GET /sso/start, GET /sso/callback, POST /api/auth/session, GET /api/auth/me, POST /api/auth/signed-out (STI Main only), POST /api/auth/local-login (local admin only), POST /api/auth/logout. Section 6 describes each.
  • Status codes: 400 validation (field errors in data), 401, 403, 404, and 409 for "period is locked" or "KPI changed since you opened it" (optimistic check on updated_at).

6. Security, access and non-functional requirements ความปลอดภัยและข้อกำหนด

Staff sign in only at STI Main, which checks the AD account and passes KPI a signed identity. KPI's own login page accepts local admin accounts only. Global roles come from the AD groups in that identity; KPI stores only per-KPI and per-unit assignments, keyed by username. Every permission is enforced on the server.

KPI has no directory access of its own, so Admin lists assignments whose username has not signed in for 90 days (from auth_session) for HR to check.

Staff sign-in through STI Main

KPI is a registered SSO client (sti-kpi) of STI Main, using the protocol STI Main already implements (SSO-Handshake.md): a one-time code in the redirect, exchanged server-to-server for an RS256 token. A user already signed in to STI Main reaches KPI with no prompt.

  1. Start. The SPA has no token (or gets a 401), so it sends the browser to /kpi/sso/start?returnUrl=…. KPI creates a random state, stores it with the return URL in a short-lived HttpOnly cookie, and redirects to STI Main's /api/sso/authorize with client_id=sti-kpi and the registered redirect_uri.
  2. STI Main. If the user has no STI Main session, STI Main shows its own sign-in page and checks the AD account (Kerberos, then LDAPS profile). It then redirects back with a one-time code (60 s).
  3. Callback. /kpi/sso/callback checks state against the cookie, then calls POST /api/sso/exchange server-to-server with the client secret (Basic auth).
  4. Validate. KPI checks the returned token against STI Main's JWKS (cached 10 min, refetched on an unknown kid): alg must be RS256, iss = the configured issuer, aud = sti-kpi, exp with 2 min skew. Anything else is refused and logged.
  5. KPI session. KPI writes an auth_session row and mints its own HS256 app token, signed with its own Auth:Jwt:Key. It carries the standard claims (username, full_name, ou, ous, groups, auth_type = AD) and expires no later than STI Main's token.
  6. Handoff. KPI redirects to the return URL with a single-use, 60-second HttpOnly handoff cookie. The SPA calls POST /api/auth/session, receives the app token in the response body and carries it as Authorization: Bearer, as the standard's lib/api.ts does. No token ever appears in a URL.
Why KPI issues its own token. One bearer format for both SSO staff and local admins; KPI's policies, audit and revocation stay inside KPI; and the standard's per-app key rule still holds, since KPI can verify STI Main's tokens but cannot mint them.

Sign-out and session checks

  • Sign-out at STI Main: STI Main calls POST /kpi/api/auth/signed-out with { username, jti, signedOutAt } and Basic sti-kpi:secret. KPI sets revoked_at on the matching auth_session; the next request with that token gets 401.
  • Backup check: STI Main keeps its issued-token list in memory, so a ping can be lost on restart. KPI therefore calls GET /api/sso/userinfo with the stored STI Main token at most every 15 minutes per active session; 401 signed_out revokes the KPI session.
  • Sign-out in KPI: revokes the KPI session, then sends the browser to STI Main so the user can end the STI Main session too.
  • Revocation check: every request checks the token's jti against auth_session (cached in memory for 60 s).
  • Groups are login-time. AD group changes take effect at the next STI Main sign-in, within one shift at most.

Local admin login (KPI's own login page)

KPI's login page, /kpi/admin/login, exists only for local administration: setup before SSO is live, and IT access when STI Main or AD is down. It is not linked from the staff navigation.

  • Local accounts only. POST /api/auth/local-login checks local_user and nothing else. It never binds to AD and never accepts an AD username/password, so staff cannot sign in there.
  • Few accounts: at most two (e.g. kpi.admin, held by IT), PBKDF2-SHA256 with 210,000 iterations and per-user salt, rotated on staff change.
  • Limited reach: the token carries auth_type = LOCAL and role LocalAdmin, valid for 2 hours. It opens the Admin module (cycles, periods, org units, scoring rules, assignments, import runs, audit log) and the health page. It cannot enter results, approve, assess, sign reviews, or read person_* data; those policies require auth_type = AD.
  • Protected: rate limit of 5 attempts per 15 minutes per IP, then a 15-minute lock; every attempt (success or failure) written to audit_log; optional allow-list restricting the page to the IT subnet.

Authorisation and data protection

  • Policies: each controller action uses an ASP.NET Core policy in KpiPolicies.cs (CanApprove, CanEnter(kpiId), CanReview(unitId), IsAdmin). React route guards and hidden buttons are UX only.
  • 401 vs 403: a missing, expired or revoked token → 401, and the SPA restarts the STI Main sign-in (step 1), which is silent if the STI Main session is still alive. A valid user requesting another team's grid → 403 with a bilingual message, e.g. "คุณไม่มีสิทธิ์บันทึกผล KPI ของทีมนี้ / You are not assigned to enter results for this team."
  • 2028 privacy: person_* rows are readable only by the person, their reviewer line, STI_KPI_Admin and STI_KPI_Executive. The repository filters in SQL on the caller's scope, not after loading. Reads of individual results are audited as well as writes.
  • Uploads: ≤ 10 MB, pdf/jpg/png/xlsx, stored on disk with a SHA-256 hash.
  • Transport: HTTPS end to end: KPI's callback, the code exchange and the sign-out ping carry codes, tokens and the client secret. TLS on the gateway is required before go-live.
  • Secrets: the SSO client secret and Auth:Jwt:Key live only in shared\config. Tokens and secrets are never logged; logs carry username and jti only.
